# Decisions

Every deviation from the brief, with the reason. The brief said to choose the
nearest workable option and record what changed rather than stopping to ask, so
this file is the record. Newest rows at the bottom of each table.

## Deviations from the brief

| # | The brief said | What was built | Why | Cost |
|---|---|---|---|---|
| 1 | Discussions need no auth: "Use `GITHUB_TOKEN` from env if present for the higher rate limit; must still work without it" | Documentation fetches unauthenticated. Discussions require a token: `GITHUB_TOKEN`, then `GH_TOKEN`, then whatever the `gh` CLI holds | GitHub serves Discussions only through its GraphQL API, and that API rejects every unauthenticated request. There is no anonymous path to fetch | A stranger cannot refetch threads without a token. Mitigated: all 300 threads are committed under `data/raw/`, so every step after the fetch runs with no token at all |
| 2 | "Discussion threads, 300, Questions category, answered only, most recent first" | The same, plus a substance floor: the accepted answer must be 120 characters or more and the question body 80 or more | GitHub marks a thread answered when someone clicks the tick, so accepted answers include "+1" and "yes". An answer with no fact in it cannot be ground truth for a missing fact. 67 threads were skipped to reach 300 | The sample is not strictly the 300 most recent answered threads, it is the 300 most recent with a usable answer |
| 3 | 60 pages: "`tutorial/` first, then `advanced/`, then top level pages" | The same rule, ordered by the mkdocs nav rather than by filename | The nav is the documentation's own reading order, so "the first 9 advanced pages" means the 9 a reader reaches first rather than the 9 that sort earliest. Deterministic either way | None. The tutorial directory holds 51 pages, so the cap is reached at 9 advanced pages and top level pages are never reached |
| 4 | `extract.py` does "sections and concepts" | Sections split in `sections.py`, concepts and edges in `extract.py` | The section split is pure line arithmetic and must never involve a model, because every evidence span is validated against the line ranges it produces. Keeping it in its own file makes that boundary visible instead of a comment | One more file than the brief listed |
| 5 | Sections are "one heading scoped chunk of a page" | A heading owns the text up to the next heading of ANY level, so nested headings do not duplicate their parent's text | Retrieval software chunks into non-overlapping pieces. Overlapping sections would let one concept be both defined and required by the same text at two levels. Same choice as the sibling repo, Will My Agent Answer This | A short parent section whose body is only an intro reads as thin, which is accurate |
| 6 | Section text is the markdown | Section text is the verbatim markdown, and code samples pulled in by FastAPI's `{* ... *}` macro are resolved and attached with their own path and line range | A reader of the published page sees that code; a reader of the raw markdown does not. Judging what a section teaches from markdown that hides its code samples would be judging a different document. 205 code files are committed under `data/raw/docs_src/` | Evidence spans can point at two kinds of file, so every edge records whether its span is prose or code |
| 7 | No file owns the `missing` field | Added `describe.py` | `missing` names an absent fact in plain words, which needs judgement, and `find.py` has to stay a deterministic function of the graph. It also has to be a different pass from validation, so that the check is not marking its own homework | One more file than the brief listed |
| 8 | "`tool.html` reads `data/findings.json`" | The explorer loads `data/site.js`, generated from `data/findings.json` by `site_data.py`, which assigns one global | Every browser blocks `fetch()` against a `file://` URL, so a page that fetched its own JSON would fail for exactly the reader who cloned the repo and opened the file. A `<script src>` is not blocked. This is what makes criterion S6 true | A generated file in the repo. It is regenerated by `run.sh` from the canonical JSON, so the two cannot drift |
| 9 | Nothing about a shared API client | Added `llm.py` | Four steps need a model and all four need the same two-path fallback. One client, no SDK, forty lines of urllib against the two APIs | One more file than the brief listed |
| 10 | Nothing about a manifest writer | Added `manifest.py` | `data/manifest.json` is specified in the brief but no file was named to write it | One more file than the brief listed |
| 11 | Extraction batches of 10 sections | Batches are one page, split when a page exceeds 12 sections or 18,000 characters. 79 batches over 570 sections | The DEFINES versus REQUIRES call turns on whether a thing is explained HERE or assumed from elsewhere on the page. A batch that cuts across pages hides the elsewhere. Page batching is also why the pilot returned zero unfindable spans | Batch sizes vary from 1 to 12 sections |
| 12 | F2 is any concept with in-degree above zero and no definition | The same, plus: referenced by at least two distinct sections, and not already reported as F1 | A concept named in exactly one section is nearly always an identifier local to that page's code sample, not something the documentation owes the reader. Excluding F1 concepts stops the explorer showing the same gap twice with less evidence the second time | F2 undercounts genuinely single-page gaps |
| 13a | One normalisation list for every span | One extra, for question spans only: if the first search fails, search again with markdown markers removed from both sides | GitHub serves a discussion body as markdown and as the plain text it renders to. The mapper reads the plain text, the file on disk holds the markdown, and the only difference is those characters. Recovered 124 of 961 proposed edges, taking the drop rate from 13 percent to 1 edge. It is still a substring search, and it is counted separately in `question_report.json` | One more branch in the validator, available to no other edge type |
| 13 | Path B seeds on sections that DEFINE the asked concepts | The same, falling back to sections that REQUIRE or MENTION the concept when nothing defines it anywhere | The near-miss case is precisely the case where nothing defines the concept, so a strict reading would hand Path B an empty context for the questions the project is about, and score it as a decline by construction. The fallback is recorded in the traversal string on every answer | Path B's seed is not always definitions, and the answers file says which |

| 14 | Nothing about re-checking the extraction | Added a definition sweep: every concept with no DEFINES edge that either two sections lean on or somebody asked about is searched for again, by an agent that greps the corpus and must produce a verbatim span | Found during the build. The first-pass prompt said not to emit a concept named after the page being read, which meant the page called "Middleware" was the one page that never recorded defining middleware, while 5 other pages recorded depending on it. The rule that was meant to suppress trivial self-reference was instead deleting the single most valuable edge on a page. The prompt is fixed for future runs; the sweep repairs the committed run and stays in the pipeline as a standing completeness check | One more model step. It is cheap and it attacks the dominant false-positive mode directly |
| 15 | Drop an edge whose concept matches the section heading | Drop an edge whose SPAN is nothing but the heading line | Same bug as row 14, from the validator side. A section titled "Middleware" explaining what middleware is should keep that edge; a span that quotes only the title evidences the title and not the claim. Recovered 7 DEFINES edges from data already on disk, at no cost | None |

## Checks that changed a number

| Check | What it found | What changed |
|---|---|---|
| Definition sweep | 74 of 164 concepts reported as defined nowhere did have a definition in the corpus, missed by the first pass | Near misses 57 to 33, orphan concepts 108 to 59. See row 14 |
| First validation round | 9 of 33 near misses valid, 0.273, below the build plan's 70 percent floor. The stop condition fired and the UI work stopped. Three causes, all mine: the concept space contained bare Python keywords and builtins, so "the FastAPI docs never explain `str`" was being reported as a gap; the first definition sweep had missed real definitions; and one finding was a name local to a code sample | Added `out_of_scope()` in find.py, rewrote the sweep prompt around the specific misses, and reran. Kept as `data/validation-round-1.json` |
| A filter that cut valid findings | While fixing the above I added a rule excluding concepts the corpus only ever shows inside code samples. It removed four findings the first round had confirmed VALID, because "appears only in code samples" is exactly what a real gap in third-party API surface looks like | The rule was removed. It survives as a reported attribute, `code_samples_only`, on every finding. A filter that silently deletes confirmed-good findings is worse than the noise it removes |
| Adjudicating the disputes | Six findings survived the fixes that round 1 had rejected. Three independent readers were given round 1's own file-and-line evidence and asked to confirm or refute it. They found round 1 wrong on four of the six: the line it cited for "port" defines *origin*, not port, and the line it cited for "host" is inside a fenced code block rather than prose | Two proposed definitions went through the span validator and both were rejected, because their spans straddle section boundaries. No edge was added. The four refuted rejections stand as findings. Round 2 then agreed unanimously on three of them, port, host and ValidationError, and marked TokenData invalid 0 of 3 |
| Second validation round | 11 of 14 valid, 0.786, Wilson [0.524, 0.924], with three independent readers per finding and 14 of 14 unanimous | Above the floor, so the build continued. Both rounds are reported in the teardown, and the first one is the more useful of the two |
| Generation prompt probe | The generation prompt I wrote added a line telling the agent what the experiment was measuring, which is a good way to change the behaviour under test. Three batches were rerun with that line removed. Declines went from 12 of 15 to 11 of 15, which is far too small a probe to detect a modest effect | Nothing. The committed answers stand, and the probe is reported as the weak check it is. The decline rate itself has a better explanation, found later during review: 282 of the 300 threads carry FastAPI's **Questions** template, not a bug-report template, and that template has the asker confirm they already read the tutorial and did not find the answer. The sample is selected for being unanswerable from the docs, so declining most of it is close to correct behaviour. An earlier version of the teardown called these bug reports, which was wrong and flattered the result |

## Environment notes

| Item | What happened |
|---|---|
| Python | 3.9.6, the system interpreter. `sentence-transformers` 3.0.1 installs and runs, but pulls `numpy` 2.x while the macOS x86_64 `torch` 2.2.2 wheel it depends on was built against the 1.x ABI, so `encode()` raises "Numpy is not available". `requirements.txt` pins `numpy<2` |
| API keys | Neither `ANTHROPIC_API_KEY` nor `OPENAI_API_KEY` was present. Every model step ran on the fallback path, in Claude Code. `llm.py` implements the API path and `llm.py selftest` exercises it, but it has not been run against a live key on this machine |
