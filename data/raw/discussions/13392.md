### Example Code

```python
from concurrent.futures import ProcessPoolExecutor

from fastapi import FastAPI, Response

app = FastAPI()

# Global process pool for offloading CPU-bound tasks.
process_pool = ProcessPoolExecutor()


def cpu_bound_task():
    total = 0
    for i in range(10**10):  # Adjust this number for desired running time
        total += i * i
    return total


@app.get("/block-cpu")
def block_cpu():
    """
    Synchronous endpoint that performs a heavy CPU-bound task inline.
    """
    cpu_bound_task()
    return {"message": "Finished CPU task inline"}


@app.get("/block-cpu-process")
def block_cpu_process():
    """
    Endpoint that offloads the CPU-bound task to a separate process.
    """
    future = process_pool.submit(cpu_bound_task)
    future.result()  # Wait for the offloaded task to complete.
    return {"message": "Finished CPU task in process"}


@app.get("/time")
def time_check():
    """
    A simple endpoint that immediately returns a 200 status code.
    """
    return Response(status_code=200)


if __name__ == "__main__":
    import uvicorn

    # Start the server using uvicorn.run.
    uvicorn.run("app:app", host="127.0.0.1", port=8000)

```


### Description

## Description

I'm experiencing a significant increase in latency on a very simple endpoint when executing a heavy CPU-bound task inline (using the default thread-based workers). In contrast, offloading the same CPU-bound work to a separate process (using a global process pool) keeps the lightweight endpoint responsive.

I expected that, since Python’s Global Interpreter Lock (GIL) is supposed to switch threads approximately every 5ms, the inline CPU-bound task wouldn't block the server for an extended period. However, the observed behavior is that the inline task causes a massive latency increase for other endpoints.

---

### `measure_time.sh`

This Bash script makes 1000 requests to the `/time` endpoint, converts the response times to milliseconds, and then calculates and prints the average and standard deviation.

```bash
#!/bin/bash
echo "Performing 1000 requests to /time endpoint..."

# Perform 1000 requests, converting each request's time from seconds to milliseconds.
for i in {1..1000}; do
    curl -s -o /dev/null -w "%{time_total}\n" http://127.0.0.1:8000/time
done | awk 'BEGIN { min=999999; max=0 }
{
    # Convert seconds to milliseconds.
    t = $1 * 1000;
    sum += t;
    sumsq += (t * t);
    if (t < min) min = t;
    if (t > max) max = t;
    count++;
} END {
    avg = sum / count;
    stddev = sqrt(sumsq / count - avg * avg);
    printf "Performed %d requests\n", count;
    printf "Average: %.4f ms\n", avg;
    printf "Stddev: %.4f ms\n", stddev;
    printf "Min: %.4f ms\n", min;
    printf "Max: %.4f ms\n", max;
}'
```

## Observed Behavior

- **Inline CPU-bound Task (****`/block-cpu`****)**:\
  When the heavy CPU-bound task is executed inline using the thread workers, the latency for the `/time` endpoint increases dramatically (100x).

- **Process-Offloaded Task (****`/block-cpu-process`****)**:\
  Offloading the CPU-bound task to a separate process maintains low latency on the `/time` endpoint (10x).

## Question

Given that the GIL should allow thread switching approximately every 5ms, why does executing a heavy CPU-bound task inline (using threads) cause such a significant latency increase for lightweight endpoints like `/time`? What factors might be contributing to this behavior, and are there any workarounds within FastAPI or Uvicorn to mitigate the issue without resorting to process-based offloading?

## Accepted answer by luzzodev (CONTRIBUTOR)

Hello @alexwilson1,
is always recommended, not only in Fastapi but in python, to run heavy cpu tasks in a different process and not threads. 
While is True that the GIL will try to switch thread every few ms, it should have the opportunity to do that. 
For example yielding a value, I/O operations and so on. 
In your case your just looping and sum a value and that will probably hold the GIL for mutch more time.
