### Example Code

```python
from fastapi import FastAPI
from pydantic import BaseModel

app = FastAPI()


class BaseItem(BaseModel):
    description: str
    type: str


class CarItem(BaseItem):
    type: str = "car"


class PlaneItem(BaseItem):
    type: str = "plane"
    size: int


items = {
    "item1": {"description": "All my friends drive a low rider", "type": "car"},
    "item2": {
        "description": "Music is my aeroplane, it's my aeroplane",
        "type": "plane",
        "size": 5,
    },
}


@app.get("/items/{item_id}", response_model=PlaneItem | CarItem)
async def read_item(item_id: str):
    return items[item_id]
```


### Description

I noticed a possible contradiction in the FastAPI documentation regarding `Union` and the use of the `|` operator with `response_model`.

In the Python 3.10+ example in the **"Union or anyOf"** section, the documentation uses:

```python
@app.get(
    "/items/{item_id}",
    response_model=PlaneItem | CarItem,
)
async def read_item(item_id: str):
    return items[item_id]
```

However, immediately below, in the **"Union in Python 3.10"** section, the documentation says:

> Because we are passing it as a value to an argument instead of putting it in a type annotation, we have to use `Union` even in Python 3.10.

It then states that using:

```python
response_model=PlaneItem | CarItem
```

would result in an error because Python would try to perform an invalid operation between `PlaneItem` and `CarItem` instead of interpreting it as a type annotation.

This seems contradictory because the Python 3.10+ example immediately above uses exactly `PlaneItem | CarItem` as the value of `response_model`.

I tested the example with a current Python/FastAPI setup, and:

```python
response_model=PlaneItem | CarItem
```

works as expected.

My understanding is that in Python 3.10+, `PlaneItem | CarItem` produces a union type at runtime, so it can be passed as the value of `response_model`. The fact that `response_model` is a runtime argument rather than a type annotation does not, by itself, mean that the `|` syntax cannot be used.

Could someone clarify whether the explanation in the **"Union in Python 3.10"** section is outdated, or whether there is some version-specific behavior that I am missing?

If the explanation is outdated, I would be happy to submit a documentation PR to clarify the wording and make the two sections consistent.

### Relevant documentation

The current Python 3.10+ example uses:

```python
response_model=PlaneItem | CarItem
```

while the following section says that the same syntax would result in an error and that `Union[...]` must be used.

I'm opening this discussion first to confirm the intended behaviour and documentation before proposing a PR. I'm happy to contribute a fix if needed

## Accepted answer by sueun-dev (NONE)

Ran the exact tutorial003_py310.py on fastapi 0.140.0 / pydantic 2.13.4 / py3.12 and it just works: item1 returns the car, item2 the plane with size, both 200, and the OpenAPI response schema comes out as anyOf of the two models. So the note is outdated. On 3.10+ `PlaneItem | CarItem` evaluates to a `types.UnionType` at runtime (PEP 604), which is exactly why passing it as the `response_model` value works.

The "must use Union, `|` would error" line is really pre-3.10 behavior, where `SomeClass | OtherClass` raises `TypeError: unsupported operand type(s) for |` (confirmed on 3.9.6). The example file itself got switched to the `|` form in the 3.10 typing-syntax upgrade, but the surrounding text stayed, so they disagree now. Updating the prose to match the example looks like the right PR.
