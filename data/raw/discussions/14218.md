### Description

I am currently working on a FastAPI application and are standardizing URL handling for consistency.
The goal is for all routes:

are case-insensitive (e.g. /A/B == /a/b)

are trailing-slash-insensitive (e.g. /path == /path/)

and that path parameters remain untouched (e.g. /A/B/{param} preserves BLABLA<<uppercase>> exactly as sent)

I have already implemented this behavior successfully using an ASGI middleware that normalizes scope["path"] before routing.

However, I feel that we could implement this more natively by extending or overriding the compile_path() function in Starlette’s routing layer.


What I did test 


I tried a CustomRoute approach by subclassing APIRoute and modifying matches() or get_route_handler(), but:

matches() runs after the router starts path matching.

Changes to scope["path"] inside that method are local and not persistent across routes.

The router continues using the original case-sensitive regex generated by compile_path().

I then examined the Starlette compile_path() implementation and noticed that route regexes are built with exact casing and strict slash matching.

This means that if we could make compile_path() emit case-insensitive regexes (for example by prefixing with (?i) or allowing optional trailing /), the behavior would be consistent across all routes without needing middleware

## Accepted answer by luzzodev (CONTRIBUTOR)

If your need is to allow this on the client side, it’s purely a URL-rewriting task that fits middleware perfectly.
If you need to standardize internal path definitions, you should also act at the routing level and ensure a consistent convention is enforced.
