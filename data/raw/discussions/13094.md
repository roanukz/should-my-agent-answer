### Description

So basically I'm trying to create a graceful shutdown for my workers after I CTRL+C.

The problem seems to be that as soon as I hit CTRL+C the workers are instantly killed, even before running the shutdown logic in the asynccontextmanager.

After the CTRL+C I get:
```
[STDERR] context canceled
Hitting this error after CTRL+C: 1
Waiting for workers to finish...
Workers finished
```

What's the proper way to handle this? Should I just intercept the SIGINT signal outside of the app and just handle FastAPI's shutdown myself? I'd like to avoid that if possible. How can I tell the workers to ignore this signal?

Also, in development I'm running my app with uvicorn's `uvicorn app:app` command.

## Accepted answer by lpares12 (NONE)

Okay, just after writing this I realized this is more of an asyncio issue than FastAPI.

A quick workaround for Windows (since it doesn't allow to intercept signals), would be to create the new process with the parameter `creationflags=subprocess.CREATE_NEW_PROCESS_GROUP`.

```
import subprocess

process = await asyncio.create_subprocess_exec(
                *run_command,
                stdout=asyncio.subprocess.PIPE,
                stderr=asyncio.subprocess.PIPE,
                creationflags=subprocess.CREATE_NEW_PROCESS_GROUP
            )
```

On Linux it would be with `preexec_fn=ignore_sigint`

```
import signal
def ignore_sigint():
    signal.signal(signal.SIGINT, signal.SIG_IGN)
    signal.signal(signal.SIGTERM, signal.SIG_IGN)

process = await asyncio.create_subprocess_exec(
                *run_command,
                stdout=asyncio.subprocess.PIPE,
                stderr=asyncio.subprocess.PIPE,
                preexec_fn=ignore_sigint
            )
```

For my use case, ignoring those signals is enough. But might be for other use cases intercepting the signals and running custom code might be a better option.
