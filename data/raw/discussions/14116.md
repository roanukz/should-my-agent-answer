### Example Code

```python
from fastapi import FastAPI, HTTPException
from fastapi.testclient import TestClient
from pydantic import BaseModel

app = FastAPI()

class TestModel(BaseModel):
    foo: str

# Middleware that throws an Exception
class TestMiddleware():
    def __init__(self, app):
        self.app = app

    async def __call__(self, scope, receive, send):
        async def receive_override():
            message = await receive()

            raise HTTPException(410, "Something bad happened")
            return message

        try:
            await self.app(scope, receive_override, send)
        except Exception as e:
            print(f"An error has occurred: {e}")
            raise

# Add an instance of starlette.BaseHTTPMiddleware earlier on the stack
# than our custom middleware.
@app.middleware("http")
async def test_func_middleware(request, call_next):
    return await call_next(request)


app.add_middleware(TestMiddleware)

@app.post("/")
def root(request: TestModel) -> TestModel:
    return TestModel(foo="bar")

client = TestClient(app)
res = client.post("/", data="{}")
print(res.status_code)
print(res.json())
```


### Description

There are two overlapping problems (or at least confusions) in the FastAPI request error handling.

1. If an error is thrown in the receive callback for ASGI middleware FastAPI catches it and returns a 400 with the description "There was an error parsing the body". This obfuscates any server-side errors and makes debugging difficult.

2. I have seen in other issues/discussions that throwing HTTPExceptions is not recommended from middleware, however on line 288 of `routing.py` ([link](https://github.com/fastapi/fastapi/blob/450a334253b1426aab08b4dea17b16ba8b4c098c/fastapi/routing.py#L288)) there is an explicit carve out for those exceptions getting thrown (and later it throws an HTTPException of it's own). However, if there is a starlette BaseHTTPMiddleware earlier on the stack than the middleware that threw the exception then what is thrown is instead a `ExceptionGroup`. Starlette wraps it's call to the rest of the middleware stack in a TaskGroup which packages it up and throws it as a different exception type ([link](https://github.com/Kludex/starlette/blob/30ae3dc77bbedd2a57ea3e0e0fccaf226961e1d9/starlette/middleware/base.py#L117)). This falls through to the catch-all exception in the FastAPI routing which then throws the 400 HTTPException with the generic description.

Essentially running this code should output printing `410` and `{'detail': 'Something bad happened'}`. But instead outputs `400` and `{'detail': 'There was an error parsing the body'}`
