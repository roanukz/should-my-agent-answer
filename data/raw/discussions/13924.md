## Accepted answer by luzzodev (CONTRIBUTOR)

I'll try to give a more detailed answer.

Once FastAPI creates the response: JSONResponse, Response, a custom subclass, etc. , it still has to encode and transmit it according to the ASGI spec. At that point FastAPI calls the response as an ASGI app: await response(scope, receive, send).

Middlewares that implement the pure ASGI interface (`__call__(self, scope, receive, send)`) only see ASGI messages (http.response.start, http.response.body, …): status code, headers, body chunks. The original Python object and its concrete class are not included in those messages. So when you say the "type is lost," is because the middleware no longer has a reference to the original subclass unless you explicitly keep it somewhere.

BaseHTTPMiddleware wraps things for you, but it buffers and rebuilds a generic Response. If you need to know the specific response class in middleware, you have to persist it yourself. Note: using BaseHTTPMiddleware is discouraged (https://github.com/encode/starlette/discussions/2160)

So: the server doesn’t "forget/lost" the type; it’s just not part of the ASGI event stream that middlewares see by default.

Said that,

> Why does the above always print starlette.middleware.base._StreamingResponse?

Because you’re using BaseHTTPMiddleware. It wraps the original response in its own internal _StreamingResponse to make streaming/body buffering simpler. So when you print(type(response)) inside that middleware, you see the wrapper, not your original JSONResponse, HTMLResponse, etc.

The same happens on the request side: the incoming request is exposed as _CachedRequest.
