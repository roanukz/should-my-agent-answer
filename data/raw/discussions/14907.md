### Example Code

```python
import logging
from logging.handlers import RotatingFileHandler
from fastapi import FastAPI, Request

logger = logging.getLogger("app")
logger.setLevel(logging.INFO)

handler = RotatingFileHandler(
    "app.log",
    maxBytes=5 * 1024 * 1024,
    backupCount=3,
    encoding="utf-8",
)

formatter = logging.Formatter(
    "%(asctime)s | %(levelname)s | %(name)s | %(message)s"
)
handler.setFormatter(formatter)
logger.addHandler(handler)

app = FastAPI()

@app.middleware("http")
async def log_requests(request: Request, call_next):
    logger.info(f"{request.method} {request.url.path}")
    response = await call_next(request)
    logger.info(f"status={response.status_code}")
    return response

@app.get("/ping")
async def ping():
    logger.info("Ping")
    return {"status": "ok"}
```


### Description

I’m looking for best practices for using a middleware logger together with internal (application-level) loggers in FastAPI, but I can’t find clear information about possible issues when logging to file(s) while running the app **with multiple workers**.

Are there any problems with file logging when using multiple Uvicorn workers?
Should I rely on Uvicorn’s built-in loggers (uvicorn.error, uvicorn.access),
and do they handle file write races automatically, or do I need to take care of this myself?

Do I need to add a unique identifier (PID) to the log file name to avoid race conditions, or should I avoid file logging when using workers?

The same question applies to running multiple Docker containers/instances: should I explicitly add a prefix or identifier to the log file name, or there is any solution to handle it automatically?

## Accepted answer by valentinDruzhinin (CONTRIBUTOR)

There are real problems with file logging when you run multiple Uvicorn workers (--workers N).

Each worker is a separate OS process. Stdlib handlers like FileHandler / RotatingFileHandler are thread-safe, but not multi-process safe. Multiple processes can interleave lines and break rotation (double-rotate, lost logs, rename clashes).

Uvicorn’s loggers (uvicorn.error, uvicorn.access) don’t fix this automatically. They’re just normal Python loggers configured by Uvicorn; if you point them at a file handler, you still have the same race unless you add a safe mechanism.

Best practice (especially in Docker/K8s): log to stdout/stderr and let the platform collect/rotate (Docker logging driver, journald, Loki/ELK, etc.).

If you must log to files on a single host:
- Use a multi-process-safe handler (file locking), e.g. concurrent-log-handler’s ConcurrentRotatingFileHandler
- Use QueueHandler/QueueListener (one writer process/thread).

As a simpler fallback: write one file per worker (PID in filename), then aggregate later.
Multiple containers/instances: don’t write all of them into the same shared file. Use stdout aggregation, or unique filenames per instance.
