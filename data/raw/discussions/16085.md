### Description

Hi FastAPI team,
 
I have a question regarding the current response serialization behavior, especially after the recent ORJSONResponse deprecation guidance.
 
While investigating the warning:
 
> FastAPI now serializes data directly to JSON bytes via Pydantic when a return type or response model is set
 
I inspected the implementation of `fastapi.routing.serialize_response()` in the version currently installed in my environment and found the following logic:
 
```python
async def serialize_response(...):
if field:
...
serializer = field.serialize_json if dump_json else field.serialize
return serializer(...)
else:
return jsonable_encoder(response_content)
```
 
To better understand when the Pydantic serialization path is selected, I temporarily patched `serialize_response()` and logged the value of `field` during request execution.
 
For an endpoint defined only with a generic return type:
 
```python
@app.get("/example")
def example() -> dict[str, Any]:
return {"hello": "world"}
```
 
the runtime output was:
 
```text
ModelField(
field_info=FieldInfo(annotation=dict[str, Any], required=True),
name='Response_example',
mode='serialization',
config=None
)
```
 
This seems to indicate that FastAPI creates a response `ModelField` even for generic return types such as `dict[str, Any]`, and therefore enters the `field.serialize()` path instead of the `jsonable_encoder()` path.
 
Based on this, I would like to confirm a few points:
 
1. Is this behavior intentional and considered part of the public/expected behavior of FastAPI?
 
2. Can users rely on a generic return type like:
 
```python
-> dict[str, Any]
-> list[dict[str, Any]]
-> list[Any]
```
 
to activate the Pydantic response serialization path, even when no explicit `response_model` is provided?
 
3. From a performance perspective, should users generally prefer:
 
```python
@app.get("/")
def endpoint() -> dict[str, Any]:
...
```
 
over:
 
```python
@app.get("/", response_class=ORJSONResponse)
def endpoint():
...
```
 
given the current deprecation warning around `ORJSONResponse`?
 
4. Are there any meaningful performance differences between:
```python
-> dict[str, Any]
```
 
and
 
```python
-> MyPydanticModel
```
 
with regard to the generated serializer and serialization speed?
 
5. Would it be worth clarifying this point in the documentation?
 
The current wording mentions "return type or response model", which many readers (including me initially) could interpret as primarily referring to Pydantic models. However, from the implementation and runtime behavior it appears that even generic typed returns such as `dict[str, Any]` participate in the Pydantic serialization path.
 
Thanks for the clarification, and for all the work on FastAPI.

## Accepted answer by LuShadowX (NONE)

Your reading of the code is right. Numbers below are from your exact versions — FastAPI 0.140.7, Pydantic 2.13.4, Python 3.13.

**1 and 2 — intentional, and yes you can rely on generics**

Any return annotation FastAPI can build a `TypeAdapter` for produces a response field, generics included:

```
route annotation                  response_field  response_class  fast path
-> (none)                         none            default         False
-> dict[str, Any]                 yes             default         True
-> list[dict[str, Any]]           yes             default         True
-> list[Any]                      yes             default         True
-> Any                            yes             default         True
-> MyModel                        yes             default         True
-> dict[str, Any] + ORJSONResponse yes            ORJSON          False
-> (none) + ORJSONResponse        none            ORJSON          False
```

Even bare `-> Any` gets one. The only ways to end up on the `jsonable_encoder` branch are to omit the annotation or to return a `Response` object yourself.

**3 — prefer the return type, and don't set both**

This is the part worth knowing. From `fastapi/routing.py` in 0.140.7:

```python
# Use the fast path (dump_json) when no custom response
# class was set and a response field with a TypeAdapter
# exists. Serializes directly to JSON bytes via Pydantic's
# Rust core, skipping the intermediate Python dict +
# json.dumps() step.
use_dump_json = response_field is not None and isinstance(
    response_class, DefaultPlaceholder
)
```

Passing `response_class=ORJSONResponse` means `response_class` is no longer a `DefaultPlaceholder`, so `use_dump_json` is `False` — you keep the response field but drop to `field.serialize` → Python objects → `ORJSONResponse.render()`. Setting both is the *slowest* of the three arrangements, not the fastest. (Both `ORJSONResponse` and `UJSONResponse` carry `@deprecated` in `fastapi/responses.py`, so the warning you hit is real, not advisory folklore.)

**4 — a model is faster than `dict[str, Any]`, and both beat the encoder path badly**

Serialization only, 20,000 iterations, best of 3, 20-key flat dict with one nested value:

```
 4.9 us   -> MyModel                        serialize_json  (fast path)
 6.1 us   -> dict[str, Any]                 serialize_json  (fast path)
13.3 us   -> dict[str, Any]                 serialize + json.dumps
48.4 us   no annotation + ORJSONResponse    jsonable_encoder + orjson.dumps
53.8 us   no annotation                     jsonable_encoder + json.dumps
 0.8 us   orjson.dumps(payload)             raw, for reference
```

The model wins by roughly 25% because `Any` has no static schema — pydantic-core has to infer each value's type at runtime, while a declared model compiles a specialized serializer.

The bigger point is the ~8x gap to the encoder rows, and it explains the deprecation: the expensive part was never `json.dumps` vs `orjson.dumps`, it was `jsonable_encoder` walking the object graph in Python. That's also why `ORJSONResponse` only ever bought ~10% here — it optimized the cheap half of the work. Absolute numbers scale with payload size and shape; the ratios held across runs.

**5 — agreed, worth documenting**

"return type or response model" is accurate but reads as if it means Pydantic models specifically. Two additions would have saved you the source dive: that *any* return annotation qualifies, `dict[str, Any]` included, and that setting a custom `response_class` silently opts you out of the fast path. The second one is the surprising half — it's easy to assume the two optimizations stack. Happy to open a docs PR if a maintainer wants it.
