### Example Code

```python
from typing import Annotated, Optional

import fastapi
import requests

app = fastapi.FastAPI()


@app.post("/")
def root(
    # note that for whatever reason, this is only different if file is the first param
    file: Annotated[Optional[bytes], fastapi.File()] = None,
    name: Annotated[Optional[str], fastapi.Body(embed=True)] = None,
):
    return name


def main():
    response = requests.post(
        url="http://localhost:8000",
        headers={
            'content-type': 'application/x-www-form-urlencoded'
        },
        data={
            'name': '',
        }
    )
    print(response.text)


if __name__ == '__main__':
    main()
```


### Description

In 0.112.3, this prints "null"
In 0.112.4, this prints ""

Note that if you change the type of name to int, it returns a 422 (`{"detail":[{"type":"int_parsing","loc":["body","name"],"msg":"Input should be a valid integer, unable to parse string as an integer","input":""}]}`) in 0.112.4

## Accepted answer by MarinPostma (CONTRIBUTOR)

This is the issue where I summarize my findings on the subject: https://github.com/fastapi/fastapi/issues/13533. TLDR, the change in behavior does not seem to be intentional. Specific codepaths were in place that handle to handle the old behavior specifically, that were unintentionally inhibited in two separate unrelated PRs. My conclusion is twofold: 1) The previous behavior was intentional, and 2) the behavior was changed by mistake.

Correctness of the old/new behavior is a different discussion. If it is decided that the new behavior is the correct one, then I the old behavior should still be supported, perhaps gated with some configuration options.
