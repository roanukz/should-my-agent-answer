### Description

### My Use Case
Before `0.118.0`, code placed after the yield in a dependency would run before sending the response.
That made it possible to structure a DB session dependency like this:
```
def get_db():
    db = SessionLocal()
    try:
        yield db
        db.commit()   # ensures commit before returning response
    finally:
        db.close()
```
This pattern is very common in tutorials and examples. It ensures that when the client receives a `201 Created`, the data is already committed and available for immediate queries.

### Problem With Current Behavior
After `0.118.0`, the code after yield runs after the response is sent, which means:
- The client may query for data it just created and receive a `404`.
- Transactions are not guaranteed to be committed at the moment the response is returned.

In effect, this changes the semantics from "_commit before responding_" to "_commit sometime after responding_".

### Why Early Closing Would Help
In my case, I need to guarantee transactional consistency at response time.
- The client depends on the resource being available immediately after receiving the response.
- Without early closing, I have to manually commit and close inside each endpoint, which removes the benefit of dependency-based session handling.

### Proposal
It would be very helpful to have an opt-in mechanism for early closing, e.g.:
- A parameter on the dependency system (yield early=True)
- Or a helper function/context manager that ensures code after yield executes before sending the response

This way, users can choose the behavior that fits their use case:
- Default: release connections late (after response) for performance/throughput.
- Opt-in: close/commit early for consistency-sensitive workflows.
