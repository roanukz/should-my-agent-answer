### Example Code

```python
@app.middleware("http")
async def test1(request, call_next):
    print("test1")
    response = await call_next(request)
    return response

@app.middleware("http")
async def test2(request, call_next):
    print("test2")
    response = await call_next(request)
    return response
```


### Description

The print result is always
"tests2"
"test1"

which is wrong because the print statement is at the top of the function and should not be affected by the await stuff, it should be sequential "test1" -> "test2". What's going on here?

Okay, so I found https://github.com/encode/starlette/issues/479, I think the documentation should explicitly state at the first paragraph that middleware calls are in reverse by their definition order if you are not using app.add_middleware() due to the "wrapping" model. I thought that the middleware was expressjs style but it wasn't.

EDIT:
I don't know if this is by design, but I have skimmed through the documentation and nothing implies that middleware is executed by the reverse order of the definition.

## Multiple middleware execution order

When you add multiple middlewares using either `@app.middleware()` decorator or `app.add_middleware()` method, each new middleware wraps the application, forming a stack. The last middleware added is the *outermost*, and the first is the *innermost*.

On the request path, the *outermost* middleware runs first.

On the response path, it runs last.

For example:

```Python
app.add_middleware(MiddlewareA)
app.add_middleware(MiddlewareB)
```

This results in the following execution order:

* **Request**: MiddlewareB → MiddlewareA → route

* **Response**: route → MiddlewareA → MiddlewareB

This stacking behavior ensures that middlewares are executed in a predictable and controllable order.
