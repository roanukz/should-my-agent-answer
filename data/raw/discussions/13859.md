### Description

It's a weird behaviour, as one flag should not affect the other, right?

## Accepted answer by luzzodev (CONTRIBUTOR)

Thank you for the update.

Unfortunately, there isn’t a combination of FastAPI settings that will give you exactly the behaviour you’re looking for. This could definitely be documented more clearly and perhaps improved in the future. Here are a few thoughts:

Model validation / serialization on an endpoint:

The `response_model` parameter (or your return-type annotation, if you omit response_model) is meant to describe the default or “happy-path” response, typically the 200 OK payload. Any attributes you add alongside it (`response_model_exclude_none`, `response_model_include`, etc.) are applied to this base response only.

All other response cases, those you would normally raise as `HTTPExceptions` or return an explicit `Response` belong in the responses={...} argument. Each entry in responses maps a status code to its own model and description, keeping the OpenAPI schema clean and explicit.

Putting it another way: `response_model` defines the primary success schema, while `responses={...}` lists every additional outcome (errors, redirects, edge cases). Mixing those two concepts in a single union often leads to confusing docs and mypy warnings.

The behaviour above is also supported by the fact that FastAPI does not validate a response body against the schema you list under a particular status code. Only the model declared via `response_model` is runtime-validated. Everything in `responses={...}` is treated as documentation.

```python
@app.get(
    "/status",
    response_model=StatusModel,           # happy-path schema
    responses={404: {"model": ErrorModel}}
)
async def get_status() -> StatusModel:
    ...
    raise HTTPException(status_code=404, detail="Not found")
```

For your use case your could write a custom exception handler, return directly the response in the "negative" cases or override the generated openapi schema. Ex: https://fastapi.tiangolo.com/advanced/additional-responses/#additional-response-with-model
