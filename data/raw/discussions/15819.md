### Example Code

```python
from fastapi import FastAPI

app = FastAPI()


@app.get("/")
def read_root():
    return {"Hello": "World"}


@app.get("/items/{item_id}")
def read_item(item_id: int, q: str | None = None):
    return {"item_id": item_id, "q": q}
```


### Description

* Create a new FastAPI environment e.g. with uv via the following
```
uv init .
echo "3.14.0" > .python-version
uv python install
uv add "fastapi[standard]"
```
* Run the example code via `uv run fastapi dev`.
FastAPI immediately segfaults:


## Accepted answer by daveshenal (NONE)

Look at the path in your  faulthandler output:

```
/Users/philip/.local/share/uv/python/cpython-3.14.0a6-macos-x86_64-none/lib/python3.14/...
```

That's not Python 3.14.0 final... it's **3.14.0 alpha 6** (`a6`). Even though your `.python-version` says `3.14.0` and `uv python install` ran without complaint, uv resolved to a stale alpha build it had cached from earlier in the 3.14 beta cycle, rather than downloading the actual final release. This is a known uv quirk. There are several open uv issues describing exactly this (astral-sh/uv#13361, #18414): a previously installed pre release CPython build gets reused/resolved instead of the version you asked for.

That fully explains the segfault. CPython alpha/beta builds are **not ABI-stable**... internal struct layouts can and do change between alpha6 and the final 3.14.0 release. `pydantic-core` (and friends like `uvloop`/`watchfiles`) ship compiled wheels built against the final 3.14 ABI. Load one of those into an alpha6 interpreter and you get a silent, traceback less SEGV - which is exactly what you saw, and exactly why it crashes deep inside `pydantic-core`'s class-creation code for `Secret` (that's the kind of code that touches CPython internals most directly).

**Fix:**

```bash
uv python list                      # confirm you have a stray cpython-3.14.0a6-... entry
uv python uninstall 3.14.0a6        # remove the alpha build
rm -rf .venv
uv python install 3.14.0            # explicit, full final version
uv run python -c "import sys; print(sys.version)"   # confirm it says 3.14.0, NOT 3.14.0a6
uv sync
uv run fastapi dev
```

If `uv python list` still offers the alpha as the resolved match for `3.14.0`, that's a uv bug worth reporting on astral-sh/uv directly... but it isn't a FastAPI or Pydantic bug.
