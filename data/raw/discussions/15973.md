### Description

I`m wrapping a sync context manager with contextmanager_in_threadpool. When __enter__ raises, I expect __exit__ to NOT be called, per PEP 343 (the context was never entered). Instead, __exit__ IS called. See the Minimal Reproducible Example (MRE).

## Accepted answer by nekoClangUage (NONE)

Thanks for confirming this Sergei @yudin-s, and for the fix. Moving `__enter__` out of the `try` fixes the first issue cleanly (and it also stops `__exit__` swallowing the `__enter__` exception when it returned `True`, which the old `except` block used to do).

I kept digging and found two more deviations from PEP 343 that the fix alone does not cover.

**2. `except Exception` skips `BaseException`**

The guard catches `Exception` but not `BaseException`. So `KeyboardInterrupt`, `SystemExit`, and `asyncio.CancelledError` raised in the body never reach `__exit__`. A standard `with` calls `__exit__` for all of these:

```python
class T:
    def __enter__(self): return self
    def __exit__(self, *a):
        print("exit called", a[0])
        return False

try:
    with T():
        raise KeyboardInterrupt()
except KeyboardInterrupt:
    pass
# standard with: exit runs, receives KeyboardInterrupt
# contextmanager_in_threadpool: exit never runs
```

So the guard needs to be `except BaseException`.

**3. Real anyio cancellation never reaches `__exit__`**

This one is sneakier. Even with `except BaseException`, a real task cancellation (via `cancel_scope.cancel()`) still does not run `__exit__`. The `await anyio.to_thread.run_sync(...)` call is itself a checkpoint: anyio sees the scope is still cancelled and re-raises `CancelledError` before the worker thread starts.

I confirmed this by canceling a task group child parked inside the context:

```python
async with anyio.create_task_group() as tg:
    async def child():
        async with contextmanager_in_threadpool(cm):
            await anyio.sleep(10)
    tg.start_soon(child)
    await anyio.sleep(0.1)
    tg.cancel_scope.cancel()
# cm.exit_called == False
```

That is the worst case for cleanup: cancellation is exactly when you want `__exit__` to run, and it is exactly when it gets skipped.

**4. The else (normal exit) branch has the same hole**

The `else` branch runs `__exit__(None, None, None)` after a body that completed without raising. Its `await anyio.to_thread.run_sync(...)` is a checkpoint too. If a cancel lands in the window between a checkpoint-free body returning and that await, `__exit__` is skipped while `__enter__` already ran - a straight resource leak. Reproducible:

```python
async with anyio.create_task_group() as tg:
    async def child():
        async with contextmanager_in_threadpool(cm):
            entered.set()   # body has no other await
    tg.start_soon(child)
    await entered.wait()
    tg.cancel_scope.cancel()
# without a shield on the else branch: cm.exit_called == False
# enter ran, exit did not
```

That window is narrow, but it is real. For a cleanup callback it should not exist at all.

**Fix: shield every `__exit__` thread call**

```python
exit_limiter = CapacityLimiter(1)
value = await run_in_threadpool(cm.__enter__)
try:
    yield value
except BaseException as e:
    with anyio.CancelScope(shield=True):
        ok = bool(
            await anyio.to_thread.run_sync(
                cm.__exit__, type(e), e, e.__traceback__, limiter=exit_limiter
            )
        )
    if not ok:
        raise
else:
    with anyio.CancelScope(shield=True):
        await anyio.to_thread.run_sync(
            cm.__exit__, None, None, None, limiter=exit_limiter
        )
```

Both `__exit__` calls are now shielded. The mental model is simple: once `__enter__` has run, `__exit__` always runs to completion, cancellation or not. This mirrors what a synchronous `with` already does: `__exit__` is a sync call, you cannot cancel it mid-flight.

Here are the tests that pin each of the cases above, so it is not just a claim. All run on both asyncio and trio (`@pytest.mark.anyio`), so the asyncio and trio variants are separate test items.

```python
class EnterFailsCM:
    def __init__(self, exit_return: bool | None = False) -> None:
        self.exit_called = False
        self.exit_return = exit_return

    def __enter__(self) -> str:
        raise ValueError("setup failed")

    def __exit__(self, exc_type, exc_val, exc_tb) -> bool | None:
        self.exit_called = True
        return self.exit_return


@pytest.mark.anyio
async def test_enter_failure_does_not_call_exit() -> None:
    cm = EnterFailsCM()
    with pytest.raises(ValueError, match="setup failed"):
        async with contextmanager_in_threadpool(cm):
            pass
    assert not cm.exit_called


@pytest.mark.anyio
async def test_enter_failure_propagates_even_if_exit_would_suppress() -> None:
    # old code: __exit__(True) would swallow the __enter__ ValueError
    cm = EnterFailsCM(exit_return=True)
    with pytest.raises(ValueError, match="setup failed"):
        async with contextmanager_in_threadpool(cm):
            pass
    assert not cm.exit_called


class ExitTrackingCM:
    def __init__(self) -> None:
        self.exit_called = False
        self.exit_args: tuple = ()

    def __enter__(self) -> str:
        return "value"

    def __exit__(self, exc_type, exc_val, exc_tb) -> bool:
        self.exit_called = True
        self.exit_args = (exc_type, exc_val, exc_tb)
        return False


@pytest.mark.anyio
async def test_keyboard_interrupt_in_body_calls_exit() -> None:
    cm = ExitTrackingCM()
    with pytest.raises(KeyboardInterrupt, match="boom"):
        async with contextmanager_in_threadpool(cm):
            raise KeyboardInterrupt("boom")
    assert cm.exit_called
    assert cm.exit_args[0] is KeyboardInterrupt


# SystemExit and manual asyncio.CancelledError are covered by two more tests
# of the same shape (test_system_exit_in_body_calls_exit,
# test_cancelled_error_in_body_calls_exit).


class SlowExitTrackingCM:
    def __init__(self) -> None:
        self.exit_called = False

    def __enter__(self) -> str:
        return "value"

    def __exit__(self, exc_type, exc_val, exc_tb) -> bool:
        self.exit_called = True
        return False


@pytest.mark.anyio
async def test_real_cancellation_still_calls_exit() -> None:
    import anyio

    cm = SlowExitTrackingCM()

    async with anyio.create_task_group() as tg:
        async def child() -> None:
            async with contextmanager_in_threadpool(cm):
                await anyio.sleep(10)

        tg.start_soon(child)
        await anyio.sleep(0.1)
        tg.cancel_scope.cancel()

    assert cm.exit_called


@pytest.mark.anyio
async def test_cancellation_after_normal_body_still_calls_exit() -> None:
    import anyio

    cm = SlowExitTrackingCM()
    entered = anyio.Event()

    async with anyio.create_task_group() as tg:
        async def child() -> None:
            async with contextmanager_in_threadpool(cm):
                entered.set()

        tg.start_soon(child)
        await entered.wait()
        tg.cancel_scope.cancel()

    assert cm.exit_called
```

The last test is the one that made me add the shield on the else branch too: without it, `assert cm.exit_called` fails on the asyncio backend (enter ran, exit did not). With the shield, it passes on both backends.

I have a full set of tests covering these cases locally. An earlier version went up as a PR but got closed/rejected, so I reworked it: the enter-out-of-try, the `BaseException` guard, and the shields on both branches are all pinned by tests now, on both asyncio and trio.

One tradeoff to flag: if `__exit__` blocks (rollback to a dead DB), cancellation cannot interrupt it until `__exit__` returns. That is the same constraint as a plain `with`, but it is worth being explicit about it.
