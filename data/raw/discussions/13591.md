You can also try on https://editor-next.swagger.io/ and type `abc` in `item_id`.
**Expected:** It should fail, as it's not a valid UUID.
**Observed:** It does not fail, and proceeds to sending it.

If you change `uuid4` for `uuid`, it will then work as expected.

The json schema (since 2019 spec) supports `uuid` format for `string` types.
https://json-schema.org/draft/2020-12/json-schema-validation#name-resource-identifiers

But, it does not have any version component.

One way of enforcing a version would be through pattern. This shows how to have `uuid` validation, even for older schema specs: https://json-schema.org/learn/file-system#diskuuid

I was initially about to submit a PR bugfix on pydantic like so:
```diff
- field_schema.update(type='string', format=f'uuid{self.uuid_version}')
+ field_schema.update(
+             type='string',
+             format='uuid',
+             pattern=rf'^[a-fA-F0-9]{{8}}-[a-fA-F0-9]{{4}}-{self.uuid_version}[a-fA-F0-9]{{3}}-[a-fA-F0-9]{{4}}-[a-fA-F0-9]{{12}}$',
+             description=f'A UUID v{self.uuid_version} identifier',
+         )
```

But when running the tests, I realized that `pydantic` was actually generating a correct JSON schema, thanks to
```python
    def __get_pydantic_core_schema__(self, source: Any, handler: GetCoreSchemaHandler) -> core_schema.CoreSchema:
        if isinstance(self, source):
            # used directly as a type
            return core_schema.uuid_schema(version=self.uuid_version)  # THIS HERE
```

## Speculations:
I'm not well-versed in the inners of pydantic. But it seems that core schema is used instead of json schema, in order to generate the json schema??
But for FastAPI, we use `__get_pydantic_json_schema__` instead, which would result in using the `uuid4` format instead of `uuid` format.

In the pydantic tests:
https://github.com/pydantic/pydantic/blob/bd1f8cf44a271e7313026faab318f3c37f23b3f4/tests/test_json_schema.py#L1065-L1081
```python
@pytest.mark.parametrize(
    'field_type,expected_schema',
    [(UUID, 'uuid'), (UUID1, 'uuid1'), (UUID3, 'uuid3'), (UUID4, 'uuid4'), (UUID5, 'uuid5')],
)
def test_uuid_types(field_type, expected_schema):
    class Model(BaseModel):
        a: field_type

    base_schema = {
        'title': 'Model',
        'type': 'object',
        'properties': {'a': {'title': 'A', 'type': 'string', 'format': 'uuid'}},
        'required': ['a'],
    }
    base_schema['properties']['a']['format'] = expected_schema

    assert Model.model_json_schema() == base_schema
```
we can see that independently on the UUIDn used, it will always generate `{'title': 'A', 'type': 'string', 'format': 'uuid'}` for the json schema.

Which is not the case for FastAPI's OpenAPI schema.

## Accepted answer by YuriiMotov (MEMBER)

It comes from Pydantic.

```py
class MyModel(BaseModel):
    id: UUID4
    name: str

print(MyModel.model_json_schema())
```
Results in:
```json
{
    "properties": {
        "id": {"format": "uuid4", "title": "Id", "type": "string"},
        "name": {"title": "Name", "type": "string"}
    },
    "required": ["id", "name"],
    "title": "MyModel",
    "type": "object"
}
```

Not sure why it's this way. `uuid4` is not a valid value for `fromat` field according to Json Schema spec.

> we can see that independently on the UUIDn used, it will always generate {'title': 'A', 'type': 'string', 'format': 'uuid'} for the json schema.

The above statement is wrong.
Look at the `base_schema['properties']['a']['format'] = expected_schema` line. It overrides the `format` field in expected `base_schema` with values like `uuid`, `uuid1`, `uuid2`, etc..

Anyway, if this is an issue, then it's an issue on Pydantic's side
