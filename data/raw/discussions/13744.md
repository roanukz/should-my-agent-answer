### Example Code

```python
from fastapi import FastAPI, Query
from fastapi.testclient import TestClient
from pydantic import BaseModel, Field, field_validator
from typing import Annotated, Any, List

class QueryModel(BaseModel):
    @classmethod
    def __init_subclass__(cls, **kwargs):
        """Adds annonations for FastAPI Query to all subclasses."""
        super().__init_subclass__(**kwargs)
        cls.A = Annotated[cls, Query()]

    @field_validator("items", check_fields=False, mode="before")  # same with "after"
    def wrap_in_list(v) -> List[Any]:
        """Puts a single value in a list, breaks comma-separated string into a list."""
        print(v, type(v))
        if isinstance(v, list):
            return [*v]
        elif "," in str(v):
            return v.split(",")
        else:
            return [v]

class MyModel(QueryModel):
    items: str|List[str] = Field()

model_params_as_str = MyModel(items="a,b")

@app.get("/")

    return qp

output:
```
a,b <class 'str'>

`AssertionError: no bueno: {'items': ['1,2']} vs {'items': ['1', '2']}`

### Description

I would like to accept query parameters as comma-separated strings or as separate items, in other words:
`?items=1,2` same as `?items=1&items=2` 

I wrote a pydantic model to accept parse the field accordingly, and the model works equivalently on both types of inputs, as expected.

But in FastAPI wraps "1,2" into a list, turning it into `[1,2]`, which doesn't work downstream.

Why does it happen and how to fix it?

## Accepted answer by luzzodev (CONTRIBUTOR)

Hello @liquidcarbon,

About Validation

You're right, this is a known issue. FastAPI preloads default values and injects them during model creation. The same behavior occurs with parameters in Form, Header, and others.

Regarding Your Use of items: str | List[str] = Field()
While the syntax `str | List[str]` is technically valid in Python 3.10+, it's strongly discouraged to mix types this way for query parameters.

Here’s why:

- Multiplicity:
    Decide upfront whether the parameter should represent a single value or multiple values. 
    Supporting both simultaneously leads to ambiguous behavior and parsing inconsistencies.

- Format Consistency:
    Although there's no hard constraint on how lists should be formatted, it's best to enforce a single, consistent convention.
    FastAPI officially supports multiple values using repeated keys: `?foo=bar&foo=baz`

This is also OpenAPI-compliant and supported by most HTTP clients and tooling.

Conclusion:

While it is technically possible to achieve what you're asking for, I don't believe it should be better supported or encouraged.
Supporting both single and multiple values in a mixed format leads to ambiguity, complicates validation, and goes against the principles of clear and consistent API design. It's better to choose one approach and design around it for clarity and maintainability.
