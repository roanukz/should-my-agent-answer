# Should commercial deploy tooling ship by default in the `[standard]` extra?

Discussion #15611 · 2026-05-26T09:08:51Z · https://github.com/fastapi/fastapi/discussions/15611

## Question

Hi Sebastián and team,

I want to raise an ergonomic / supply-chain-hygiene question about a change in fastapi `0.136.3`, *not* as a complaint about the underlying choice but as feedback on how it lands for downstream maintainers and security tooling. I'm a fastapi user shipping a framework that depends on fastapi transitively.

### Context

In `0.136.3`, the `[standard]` extras group gained two transitive deps via `fastapi-cli[standard]` → `fastapi-cloud-cli`:

- `fastar>=0.9.0` — Rust tar bindings, used by `fastapi-cloud-cli/commands/deploy.py:127` to write zstd-compressed tarballs for cloud upload. Completely legitimate; the name is `fast`+`tar`.
- `sentry-sdk`, `rignore`, etc. — telemetry + Rust-backed gitignore parsing for the deploy flow.

`pyproject.toml` cleanly declares both `standard` and the new `standard-no-fastapi-cloud-cli` extras — so opt-out exists for users who want it, which I appreciate.

### What's happened downstream

The Amazon Inspector vulnerability database has issued advisory `MAL-2026-4750` flagging `0.136.3` as a malicious release. The advisory's substantive claims are wrong (`fastar` is not a typosquat, the dep has a legitimate purpose, the opt-out extra demonstrates intentional design), but pip-audit + similar tooling propagate the finding to every project that resolves `fastapi==0.136.3`. As of writing, every downstream project running `pip-audit --strict` in CI is red-blocked. The advisory will probably be retracted eventually, but in the meantime maintainers across the ecosystem are pinning `!=0.136.3` defensively.

That's not your responsibility to fix and I don't think you owe anyone a response to it. But it surfaces a real ergonomic question that I think *is* worth a conversation:

### The actual question

The canonical install doc still says `pip install "fastapi[standard]"`. With `0.136.3`, this:

1. Adds commercial-deploy tooling (`fastapi-cloud-cli` → FastAPI Cloud) to the default-recommended install path.
2. Pulls in Rust-backed deps with single-maintainer authorship (`fastar`, `rignore`).
3. Adds outbound-network telemetry (`sentry-sdk`).

The opt-out extra (`standard-no-fastapi-cloud-cli`) exists, which is great — but it requires users to (a) know the cloud-cli is now bundled, (b) know they don't want it, and (c) remember to type a much longer extras name. Most users following the official docs will install the full `[standard]`.

**Would the team consider one of these?**

- **(A)** Promote `standard-no-fastapi-cloud-cli` (perhaps under a shorter name like `serve` or `core-standard`) to be the *primary* recommended install, with `[standard]` opt-in for cloud-cli users.
- **(B)** Leave the resolution as-is but add a clearer call-out in the `[standard]` install docs that it now bundles commercial deploy tooling, with a one-liner pointer to the opt-out extra.
- **(C)** Move `fastar` and the other cloud-cli-specific transitive deps so they're declared in `fastapi-cloud-cli`'s own `[standard]` (which they are, currently) but *not* re-declared in fastapi's `[standard]` — i.e. let users get them only when they install `fastapi-cli[standard]` explicitly. (This may already be the structure; I haven't fully traced it.)

None of these is urgent. The current shape is defensible — I'm only flagging the question because a lot of downstream maintainers got a confusing CI red today, and the trajectory of "framework's recommended install path silently grows commercial tooling" is worth a moment of explicit thought even if the outcome is "yes, that's the trade-off we're making."

Thanks for fastapi. Happy to provide more context on the pip-audit failure path if useful.

## Accepted answer by tiangolo (MEMBER)

Thanks for the comment!

About the false positive from Amazon, more of the context is here: https://github.com/ossf/malicious-packages/issues/1274 , it seems it was an automated AI scan that reported a vulnerability, got accepted, created a CVE, etc. without ever even attempting to contact us. :smiling_face_with_tear:  But they are withdrawing it now.

About single-maintainer dependencies, that's how most of the entire open source ecosystem works, in most cases works fine, and in most cases there's one specific person (or a very small few) leading a project, that's not really an issue. The fact that it's under a person's username also doesn't limit permissions to maintain, they could add extra people. Same with an org, the fact that it's an org doesn't necessarily change things, it could still be a single person leading.

About the default `standard` dependencies, your option C is what already is in place, sadly, the automated detection didn't even check that.

About how to explain what is installed and done, we do that profusely, it's in the docs, sadly there's no easy way to explain more than that. We don't have a direct channel with users, not even telemetry. Sentry is installed for the cloud CLI for when there are errors deploying, but that's not activated when running the regular FastAPI commands. It would be very useful to know what things people use and what not, to be able to deprecate things, but we don't do that as that would raise concerns, it's only for cloud users.

The current decision to make those things part of `standard` is that that is the standard experience I would think users could get by default:

* It is designed to be the default, official, and simplest way to deploy FastAPI to the cloud. Anyone can deploy it to any other platform, but that is the one made by and for FastAPI.
* The default is made to be the one with the lowest friction, if a user needs to perform a bunch of additional steps just to get the recommended experience of deploying, then it's not as straightforward as it should it, which is also the spirit of FastAPI in general, to have good defaults on. Important in particular to newcomers to FastAPI and Python.
* It is already opt-in, people have to install `"fastapi[standard]"` to get that plus the other things (e.g. uvloop and httptools for high performance). But if they simply install `fastapi`, they won't get any of that.
* FastAPI Cloud is also our way of sustainability for the open source projects, and it's quite aligned with them, as the more effectively people can use Python and the open source tools, more potential clients down the line for the company, so it's aligned even if it was independent of me.

## What needs attention and fixing: automated AI reports

Now, I want to raise an important issue that is not discussed in the original post, that should probably get attention, and I don't know the right way to solve it.

AI automated tools from organizations with access to create CVEs directly should not go and create them based on an AI hunch. 

First, these things should be responsibly disclosed to the projects, in private, allowing handling of the vulnerability properly, not reporting via a third party, and then us getting to know about a "vulnerability in FastAPI" via users complaining. That's quite wrong.

Second, if they flag something, that should be reviewed by human researchers before reporting.

Third, the combination of giving some AI authorization to automatically create CVEs seems quite dangerous to me. That should definitely have a human review.

I use AI a lot, I appreciate how much it helps, but that's the wrong way to use it.

Anyway, I don't have a way to solve that, I don't expect you would, but I wanted to highlight an important factor in this situation that causes a lot of friction and I don't think should simply go unnoticed.
