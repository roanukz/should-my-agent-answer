### Example Code

```python
import asyncio
import time

import aiosqlite
from fastapi import FastAPI

app = FastAPI(debug=True)


@app.get("/async/products")
async def get_products_with_orders_async():
    start_time = time.time()

    async with aiosqlite.connect("shop.db") as db:
        async with db.execute("""
            SELECT p.*, COUNT(o.id) as order_count 
            FROM products p 
            LEFT JOIN orders o ON p.id = o.product_id 
            GROUP BY p.id
        """) as cursor:
            products = await cursor.fetchall()

        # Process products concurrently
        async def process_product(product):
            # Calculate same metrics
            stock_value = product[2] * product[3]
            order_count = product[4]
            popularity_score = order_count / (product[3] + 1)

            return {
                "id": product[0],
                "name": product[1],
                "price": product[2],
                "stock": product[3],
                "order_count": order_count,
                "stock_value": stock_value,
                "popularity_score": popularity_score,
            }

        tasks = [process_product(product) for product in products]
        processed_products = await asyncio.gather(*tasks)

    return {
        "type": "asynchronous",
        "time_taken": time.time() - start_time,
        "products": processed_products,
    }
```

## Accepted answer by luzzodev (CONTRIBUTOR)

Now i can answer with a better prospective.

From what I see, your main concern is about the thread limitation and how it can impact scalability and performance. This limitation doesn't come from FastAPI itself but from AnyIO, and it’s not an unverified claim—it's well documented here: [AnyIO Thread Limits](https://anyio.readthedocs.io/en/stable/threads.html#adjusting-the-default-maximum-worker-thread-count).
What happens is that, after reaching the thread pool limit, incoming requests are first queued in the network queue. Once the queue reaches its maximum size, any additional requests are discarded. This can lead to failed or rejected requests if the system is overloaded and unable to process them within the limits of available threads and queue capacity.

At that scale "hundreds of thousands" you should pick FastApi for what it is, an asynchronus framework. While you can still increase the size of threadpool limit and manage the loadbalancer ( something that you should do in any case) this could results to be very expencive or inefficient. 

Complexity of Refactor:  in general you should never block the main loop even with sync code (that's why sync code is run in a different thread). 

What i'm saying about picking the right tool is that, while FastApi is a great framework, it doesn't have the magic recipe to fit all use cases and, at that scale, using it in a sync way could not be the best choice.
