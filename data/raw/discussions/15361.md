### Description


# Proposal: Add CBV (Class-Based View) and CBR (Class-Based Router) to enrich FastAPI routing capabilities

## Background & Current Routing Status
FastAPI is a powerful and high-performance web framework that officially provides native **function-based routing**, which is concise, intuitive, and very suitable for stateless lightweight APIs. However, in real-world complex business development scenarios, the current routing system has obvious limitations:

1. **Official function-based routing**
It is the standard and recommended way of FastAPI, perfect for simple and stateless endpoints. But it is difficult to encapsulate stateful business logic such as shared database connections, configuration files, common services, and dependency injection.

2. **Community CBV (Class-Based View) implementations**
Many community solutions have implemented class-based views for fine-grained control of a single resource. However, they all require **manual route binding**, which is completely inconsistent with FastAPI’s official decorator-style automatic route binding, leading to fragmented coding styles and increased learning and maintenance costs.

3. **CBR (Class-Based Router) — designed for real business modules**
I have developed a new CBR pattern based on actual production development requirements. Unlike CBV which focuses on a single resource, CBR is oriented to business modules. It supports shared dependencies, configurations, database instances, and other reusable logic while maintaining high flexibility and strong encapsulation, filling the gap between function-based routing and resource-based CBV.

## Key Advantages of My Implementation
I have implemented CBV and CBR with strict alignment to FastAPI’s native design philosophy:
- Zero external dependencies, only based on FastAPI and Starlette native APIs
- Extremely lightweight: only 132 lines of code including comments
- No black magic, all logic is transparent and easy to understand and maintain
- Fully consistent with the official decorator style, just like `@app.get` / `@app.post`
- Seamlessly compatible with APIRouter and native function routing
- Can coexist with all existing routing patterns without any intrusion
- Supports instance initialization parameters, making dependency injection more elegant

###  Merge Multiple Independent Apps (Werkzeug-Style Mount)
```python
from fastapi import FastAPI, APIRouter
from fastapi.cbx import cbv, cbr, get

# Function-based app
func_app = FastAPI(title="Function App")
@func_app.get("/test")
def func_test():
    return {"app": "func", "msg": "Native function route"}

# CBV-based app
@cbv(prefix="/cbv", router=APIRouter())
class CBVApp:
    def __init__(self):
        self.msg = "CBV independent app"
    def get(self):
        return {"app": "cbv", "msg": self.msg}

cbv_app = FastAPI(title="CBV App")
cbv_instance = CBVApp()
cbv_app.include_router(cbv_instance.router)

# CBR-based app
@cbr(prefix="/cbr", router=APIRouter())
class CBRApp:
    def __init__(self):
        self.msg = "CBR independent app"
    @get("/test")
    def test(self):
        return {"app": "cbr", "msg": self.msg}

cbr_app = FastAPI(title="CBR App")
cbr_instance = CBRApp()
cbr_app.include_router(cbr_instance.router)

# Main merged app
app = FastAPI(title="Main Entry")
app.mount("/func", func_app)
app.mount("/cbv", cbv_app)
app.mount("/cbr", cbr_app)

```

Thank you for taking the time to review my proposal and sharing your valuable experience with class-based patterns in FastAPI production environments. Your insights about the relationship between dependency injection and class instantiation are indeed a crucial discussion point in the FastAPI community.
 
Regarding your concerns, I'd like to clarify a few points about CBX's design philosophy:
 
CBX is a lightweight, non-invasive wrapper.
CBX doesn't reimplement or bypass FastAPI's routing and DI system. It simply provides a minimal mechanism for binding class methods to routes. All actual routing, parameter parsing, dependency resolution, async handling, etc., remain delegated to FastAPI's native machinery. Therefore, once properly bound, features like OpenAPI generation, hot reload, and async support should behave identically to standard function-based routes.
 
Design focus: Class-based routing for simple scenarios
CBX targets straightforward use cases where developers prefer class-based organization without complex dependency injection needs. We intentionally leave initialization control entirely to the user—they decide when and how to instantiate (e.g., at app startup, or via a factory per request). This maintains flexibility while avoiding overlap with FastAPI's built-in Depends() system.
As you correctly noted, mixing Depends() in init would conflict with FastAPI's request-scoped DI. CBX's approach is to stay out of that territory, serving as a lightweight complement to the official DI patterns, focused purely on expressive routing.
 
Testing and compatibility
Your points about test coverage and compatibility are well-taken. I've already added comprehensive tests locally (async methods, OpenAPI schema, path/query params, etc.) and will continue improving them. If the FastAPI team considers it valuable, I'm happy to integrate these tests into the official CI pipeline to ensure ongoing compatibility.
 
CBX isn't meant to replace existing DI patterns. Rather, it offers an alternative for developers who prefer class-based views in simple scenarios—rapid prototyping, internal tools, or migrating existing class structures to FastAPI. Its value lies in minimal API surface and near-zero learning curve.
