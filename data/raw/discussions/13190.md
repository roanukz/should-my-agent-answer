### Example Code

```python
from fastapi import FastAPI
import logging
import uvicorn
import sys

FMT = "%(asctime)s %(levelname)s [%(name)s] trace_id=%(otelTraceID)s span_id=%(otelSpanID)s resource.service.name=%(otelServiceName)s | %(message)s"

console = logging.StreamHandler(stream=sys.stdout)
console.setFormatter(logging.Formatter(FMT))

logger = logging.getLogger(__name__)
logger.addHandler(console)
logger.setLevel(logging.DEBUG)


app = FastAPI()


@app.get("/")
def index():
    logger.info("Handling request")
    return {"hello": "world"}


@app.middleware("http")
async def middle(request, call_next):
    logger.info("In middleware, before call_next()")
    response = await call_next(request)
    logger.info("In middleware, after call_next()")
    return response


if __name__ == '__main__':
    log_config = uvicorn.config.LOGGING_CONFIG
    log_config["formatters"]["access"]["fmt"] = FMT
    logger.info("Starting app...")
    uvicorn.run("__main__:app", host='0.0.0.0', port=8082, log_config=log_config, reload=False)
```


### Description

In a Python/Uvicorn/FastAPI application, auto-instrumented with OpenTelemetry through `opentelemetry-bootstrap -a install` and `opentelemetry-instrument python main.py`, the use of a HTTP middleware seems to lose the request context that allows OpenTelemetry to know about the current span and its spanId/traceId.

Note: I'm not sure if I should be asking/reporting this here, or in Starlette, or Uvicorn, or OpenTelemetry 😬 

This is particularly problematic as it prevents the Uvicorn access log from correctly logging the traceId/spanId of the request being logged.

Here's the log output of a `GET /` request with the middleware enabled:

```
2025-01-09 18:54:23,082 INFO [__main__] trace_id=0 span_id=0 resource.service.name=test | In middleware, before call_next()
2025-01-09 18:54:23,083 INFO [__main__] trace_id=d8036804a0ca2c5352871a78492958bf span_id=18d9b917834b5047 resource.service.name=test | Handling request
2025-01-09 18:54:23,083 INFO [__main__] trace_id=0 span_id=0 resource.service.name=test | In middleware, after call_next()
2025-01-09 18:54:23,083 INFO [uvicorn.access] trace_id=0 span_id=0 resource.service.name=test | 127.0.0.1:63889 - "GET / HTTP/1.1" 200
```

Notice that neither the middleware (before and after the inner request handling), nor the Uvicorn access log, have `trace_id` and `span_id` set.

But when commenting out the middleware, this works:

```
2025-01-09 18:54:05,803 INFO [__main__] trace_id=96c59e465aff3d90481efac9cd6f9194 span_id=6013411f61f4c90d resource.service.name=test | Handling request
2025-01-09 18:54:05,804 INFO [uvicorn.access] trace_id=96c59e465aff3d90481efac9cd6f9194 span_id=6013411f61f4c90d resource.service.name=test | 127.0.0.1:63881 - "GET / HTTP/1.1" 200
```

Looking at the code of `BaseHTTPMiddleware` it looks like it schedules the inner `call_next` in a `anyio.task_group` – maybe the request context gets lost through that?
