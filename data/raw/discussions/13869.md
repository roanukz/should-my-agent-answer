=== Code of the LTU cache

def weak_lru_cache(maxsize=1, typed=False, ttl=None):
    """LRU Cache decorator that keeps a weak reference to self

    Warning: When used in a class, the class should implement __eq__(self, other) and __hash__(self) methods

    Source: https://stackoverflow.com/a/55990799"""

    def wrapper(func):
        @functools.lru_cache(maxsize, typed)
        def _func(_self, *args, ttl_hash=None, **kwargs):
            del ttl_hash  # Unused parameter, but kept for compatibility
            return func(_self(), *args, **kwargs)

        @functools.wraps(func)
        def inner(self, *args, **kwargs):
            return _func(weakref.ref(self), *args, ttl_hash=_get_ttl_hash(ttl), **kwargs)

        return inner

    return wrapper

### Description

Unfortunately, when Glances is integrated in Home Assistant, it crashs with the following error:

    httpx.RemoteProtocolError: peer closed connection without sending complete message body (received 0 bytes, expected 29904)

See detail here: https://github.com/nicolargo/glances/issues/3238

When i comment the LRU cache:

    #@weak_lru_cache(maxsize=1, ttl=1)
    ...

Then everything work fine....

Any idea where the issue came from ?

## Accepted answer by luzzodev (CONTRIBUTOR)

Hello @nicolargo,

I cloned your project and debugged the issue so I could give you a more detailed answer.

I suspected from the start that the problem was not caching the computed value, but rather caching the entire response instance.
The issue isn’t limited to the OS you mentioned, it can potentially affect any OS and it stems from a side effect applied to the response headers.

How I tested it
I disabled TTL generation so the cached response would always be returned.

What happens
The Gzip middleware, in addition to compressing the body, also adds or rewrites certain headers such as Content-Length and Content-Encoding.
This operation modifies those headers inside your cached response (a side effect).
On the next request (a cache hit), the headers are not recalculated because that only happens when the response is first created.
The response passes through the Gzip middleware again, but, based on the existing headers, the middleware forwards it directly, assuming it has already been compressed.
At that point an exception is raised because the declared length no longer matches the actual body.

Hope this helps =)
