### Example Code

```python
import uvicorn
from fastapi import FastAPI, Request

app = FastAPI(root_path='/prefix')

@app.get('/subpath/', name='subpath')
def with_prefix(request: Request):
    return request.app.url_path_for('subpath')


uvicorn.run(app)
```


### Description

# Behavior
Request different variations of paths using curl exhibits this behavior:

- `http://localhost:8000/subpath/` -> 200, `/subpath/`
- `http://localhost:8000/subpath` -> 307, Location: `http://localhost:8000/subpath/`
- `http://localhost:8000/prefix/subpath/` --> 200, `/subpath/`
- `http://localhost:8000/prefix/subpath` --> 307, `http://localhost:8000/prefix/subpath/`

I request the paths without the trailing slash to trigger the automatic redirects and see the behavior for that, as well as the URL generation.
My use-case is to deploy an application behind a reverse proxy that delegates traffic starting with `/prefix` to the fastapi application.

# Deployment options
I see two ways of doing this: with, and without stripping the `/prefix` in the reverse proxy.

## Stripping the prefix
This is the deployment option I assume to be the default in such scenarios.
It would trigger the behavior of the first two paths above. 
In this case, URLs returned from the application need to be prefixed with `/prefix`. 
My expectation was, that setting `root_path` would achieve this, which it doesn't. 
The URLs generated using `url_path_for` I can modify manually (`request.scope.get('root_path') + request.app.url_path_for(...)`). 
For the URLs generated by the automatic redirection I have yet to find a way of achieving this.

## Not stripping the prefix
For this one the latter two paths are the relevant ones, in this case there's a mismatch between the URLs generated by redirects and for `url_path_for`.
While the URLs generated by my application can be manually adapted as described above, I find this inconsistent with the redirect behavior and it makes the code non-root-path agnostic, even if it is possible to write a dynamic generation that works for any `root_path`.

# Conclusion
I am confused by this behavior, my expectation would've been the one I describe in the first deployment option.
Because I consider the first option to be more common, I feel that I am overlooking something, because I cannot find a way to be able to deploy my application in this way.
In the second case, the behavior is inconsistent between different URL generation methods.

It seems like the current behavior allows both methods at the same time.
Instead I expected to see 404s on the requests that include the root_path.
Moreover I believe there might even be some ambiguity when the `root_path` is the same as a route provided by the application.
Consider list and detail endpoints `/foo/` and `/foo/{slug}/`, with the root path `foo`. A request to `/foo/foo/` could be considered as either the former or the latter.
Of course this example is artificial, but I don't think a similar scenario may occur in the real world.
Edit: I just checked this scenario, and in fact this will shadow the non-root-path prefixed requests, having them yield a 404.

Please help me understand this better.

## Accepted answer by YuriiMotov (MEMBER)

So, I think this discussion is resolved now.

* When `root_path` parameter is passed to `FastAPI()` you should use URLs with prefixes (proxy shouldn't strip prefix). So, `http://localhost:8000/subpath/` and `http://localhost:8000/subpath` from initial post are not valid paths.
* Use `request.url_for()` for URL generation instead of ~~`app.url_path_for()`~~
