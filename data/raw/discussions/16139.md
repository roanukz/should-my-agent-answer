### Example Code

```python
from fastapi import FastAPI, Query

app = FastAPI()


@app.get("/items")
def read_items(
    limit: Annotated[
        int,
        Query(
            ge=1,
            le=100,
            description="Maximum number of items",
        ),
    ] = 10,
):
    return {"limit": limit}
```


### Description

While working with FastAPI and Pydantic v2, I noticed a difference in how defaults are specified when using `Annotated`.

With Pydantic, defaults can be declared inside `Field()`, which keeps all field-related configuration together:

```python
from typing import Annotated

from pydantic import BaseModel, Field


class Item(BaseModel):
    name: Annotated[
        str,
        Field(
            default="John",
            min_length=1,
        ),
    ]
```

However, FastAPI parameter helper functions such as `Query()` currently require the default value to be specified outside `Annotated`:

```python
from typing import Annotated

from fastapi import Query


limit: Annotated[
    int,
    Query(
        ge=1,
        le=100,
        description="Maximum number of items",
    ),
] = 10
```

I was wondering whether FastAPI could support an additional syntax such as:

```python
limit: Annotated[
    int,
    Query(
        default=10,
        ge=1,
        le=100,
        description="Maximum number of items",
    ),
]
```

or any equivalent approach.

I'm **not suggesting replacing the current syntax**. My question is whether this could be supported as an **additional, backward-compatible** option.

### Why I think it could be useful

- Keeps the default value together with the rest of the parameter metadata.
- Feels more consistent with Pydantic v2's `Field(default=...)` style.
- Improves readability for parameters with multiple validation constraints.
- Provides a single location for parameter configuration.

### My question

Is there an intentional design reason why FastAPI keeps the default value in the function signature instead of allowing it inside parameter helper functions like `Query()`, `Header()`, `Cookie()`, `Body()`, etc.?

Or could supporting this be considered as a future enhancement while preserving the current syntax?

Thanks!

## Accepted answer by AKzar1el (NONE)

It's mostly the latter: Pydantic can interpret the `Annotated` metadata at runtime, but that doesn't mean static type checkers understand a default placed inside it.

Pydantic's own docs call this out explicitly: `default`, `default_factory`, and `alias` affect the synthesized `__init__()`, but those arguments are **not understood by static type checkers when they're provided through the `Annotated` pattern**. For those cases, Pydantic recommends the normal assignment form instead.

So this:

```python
class Item(BaseModel):
    name: Annotated[str, Field(default="John")]
````

can be understood by Pydantic at runtime as having a default, but the `Field(...)` metadata itself doesn't redefine the annotation for a normal type checker.

That's also why the FastAPI/function case is more constrained:

```python
def read_items(
    limit: Annotated[int, Query(default=10)],
):
    ...
```

Regardless of how FastAPI interprets that metadata at runtime, Python's actual function signature still has **no default value** there:

```python
read_items()  # missing required argument
```

Whereas:

```python
def read_items(
    limit: Annotated[int, Query(ge=1, le=100)] = 10,
):
    ...
```

has a real Python default. That is visible to `inspect.signature()`, direct callers, IDEs, and static type checkers without any FastAPI-specific interpretation.

So Pydantic isn't getting a special general capability from `Annotated` that FastAPI could reuse here. Pydantic can consume the metadata while constructing a model at runtime, while FastAPI still has to preserve the semantics of an ordinary Python function signature.

Pydantic documents the static-checking limitation here:
[https://docs.pydantic.dev/latest/concepts/fields/#the-annotated-pattern](https://docs.pydantic.dev/latest/concepts/fields/#the-annotated-pattern)

FastAPI documents the same reason for keeping the real default outside `Query()` here:
[https://fastapi.tiangolo.com/tutorial/query-params-str-validations/#query-as-the-default-value-or-in-annotated](https://fastapi.tiangolo.com/tutorial/query-params-str-validations/#query-as-the-default-value-or-in-annotated)
