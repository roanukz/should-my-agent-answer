### Description

I am trying to learn and better understand async workflows with FastAPI. As such I wanted to test 3 scenarios:

1. Normal def routes with sqlmodel+postgres+psycopg2
2. Async def routes with sqlmodel+postgres+psycopg2
3. Async def routes with sqlmodel+postgres+asyncpg

I am evaluating the three scenarios using  [locust](https://locust.io/). I am running this on my local machine, i.e. I start both the FastAPI server (`uv run fastapi dev`) and the locust server locally. I am using the following `locustfile.py`:

```py
from locust import HttpUser, task

class Items(HttpUser):
  @task
  def get_items(self):
    self.client.get("/items")

  @task
  def create_item(self):
    self.client.post(
      "/items/create",
      json={**multiple fields**},
    )
```

This just means that every locust user I specify will continously call these two endpoints. I then create 20 users and let them send requests until roughly 50k requests have been accumulated. I obtained the following results:

- Async routes with sync db (postgres+psycopg2) operations. (Run 1 on the image below)
  - Requests per second: ~220

- Async routes with async db (postgres+asyncpg) operations. (Run 2 on the image below)
  - Requests per second: ~170
  - Response time (ms):
    - 50th percentile: ~110

  - Response time (ms):

Based on my understanding what I was expecting (and probably hoping) to see was the following ordering performance wise (from best to worst):

1. Full async (async def routes + async db operations).

```Py
from sqlalchemy.ext.asyncio import async_sessionmaker, create_async_engine
```

Anything you can spot wrong with the async setup? Or perhaps my locust setup? Or anything else?

## Accepted answer by luzzodev (CONTRIBUTOR)

Hi @jandonov,

When conducting a benchmark to analyze different scenarios and compare various approaches, it’s crucial to ensure the test scenario is well-designed and accurately reflects what you intend to measure.

In your case, there are several issues that likely influenced the results you observed:

### 1. Isolation
Running all components on the same machine can introduce noise. The sync and async approaches may impose different loads on the system, and those variations can affect performance outcomes. If your goal is to compare the two models purely, this introduces a variable that should be excluded. However, if you're evaluating them within a closed system setup, then including that factor is valid.

### 2. Context
Concurrency and parallelism are not the same—they're often treated interchangeably but have fundamentally different strengths and limitations, often opposing ones. Understanding which applies to your scenario is essential.

### 3. Benchmark Accuracy
You must ensure your benchmark aligns correctly with the metrics you intend to measure.


### Back to Your Benchmark

**What does your test represent?**
It appears to simulate a scenario where a maximum of 20 concurrent requests are made, with database response times being nearly negligible (e.g., empty DB, simple queries, local machine).

**Are the results expected?**
Absolutely. Parallelism doesn’t incur the overhead that concurrency does. Threads are managed in a pool, and with minimal processing time, their efficiency is high. In other words, you're comparing 25 workers handling quick requests in parallel with a single worker processing 25 requests piece by piece.

Here you have another example:
Run 1 Sync -> using time.sleep(0.05)
RT: 53ms
Run 2 Async  -> using asyncio.sleep(0.05)
RT: 73
![benchmark](https://github.com/user-attachments/assets/8b7739f0-bf12-45fb-bb7c-1e72744c17cd)
Whether you're handling 50k or 500k total requests just changes the test's duration, not its structure.

For your specific benchmark only you should expect:
1 Full sync (normal def rouets + synd db operations).
2. Full async (async def routes + async db operations).
3. Mixed (async def rouets + sync db operations).  

If the blocking time from the query is less then concurrency overhead or if is so small to be ignored you can switch for sure 2 with 3.



**What's Missing in the Test?**
You’re overlooking the benefits and role of concurrency.
What happens with 200 users instead of 20 (still with 50k total requests)?

With parallelism, you might cap at 40 available workers, and additional requests will queue or get dropped. In contrast, with async, those extra requests can still be handled concurrently by each worker, allowing better throughput.

**What if the endpoint has longer processing times?**
The longer the wait, the greater the advantage of async. Async efficiency increases while thread-based parallelism drops off due to idle resource consumption during wait periods.

These are fundamentally concurrency vs. parallelism considerations, not just FastAPI-specific ones.
Another Important Point

Locust simulates load based on users, not requests per second. This is a significant difference. In your case, RPS is a derived metric, not the true throughput. So if the number of users doesn’t exceed your worker limit (e.g., 40), the test always compares direct thread calls vs. the overhead of concurrent execution.

In your case, you're not really measuring the server’s maximum RPS, you're measuring what 20 users can produce.

**Conclusions**
In general, parallel calls are faster to execute than concurrent ones. However, their major limitation is scalability. You can typically handle far more concurrent requests than parallel ones. The sweet spot is to combine both approaches: use multiple workers, each handling requests concurrently.

**Simplified Final Example**
Imagine an endpoint calling an AI inference service via HTTP, which takes 5 seconds to respond, and 100 requests arrive simultaneously.
Sync (Thread) Scenario

```
  t=0   → 100 queued, 0 processed  
  t=5   → 80 queued, 20 processed  
  t=10  → 60 queued, 40 processed  
  t=15  → 40 queued, 60 processed  
  t=20  → 20 queued, 80 processed  
  t=25  → 0 queued, 100 processed  
```

Async Scenario
```
  t=0       → 100 queued, 0 processed  
  t≈5 to 10 → 0 queued, 100 processed  
```

Here, while each sync call may be slightly faster per execution, threads are blocked the entire time, wasting resources. 
Even if async takes 5.005 seconds per call (due to overhead), it allows the server to process other requests during that wait, massively increasing throughput.
