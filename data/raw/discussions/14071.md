There is no duplicated error log here,  the trace is consistent and is logged by **uvicorn**.

### On the use of `BaseHTTPMiddleware`

Let me give you a bit of context regarding the use of middlewares, and in particular the `BaseHTTPMiddleware` you are relying on.
The implementation of `BaseHTTPMiddleware` in **Starlette** (and inherited by **FastAPI**) has been the subject of long discussions and many issues. At some point, it was even considered for deprecation.

Nowadays, its use is **discouraged** due to the number of problems that arise from its implementation. It is still maintained mainly because it provides a higher-level abstraction compared to an **ASGI middleware**. That abstraction can be very convenient in simple cases or for developers just starting with middlewares.

That being said, if you need more control or are building more complex applications, it is usually better (and recommended) to implement a middleware directly following the **ASGI** specification. This gives you full control over the request/response lifecycle.

Sources:
https://github.com/Kludex/starlette/discussions/2160
https://www.starlette.io/middleware/#basehttpmiddleware
https://www.starlette.io/middleware/#pure-asgi-middleware

### About error handling

As for error handling, the suggestion from @saky-semicolon is correct, with a small clarification.
Exception handlers for status code `500` or the base `Exception` class are registered by **Starlette** at the outermost layer of your application. This ensures that any exception raised deeper in the stack (endpoints, middlewares, etc.) will still, whenever possible, produce a proper response.

To be totally honest, I don’t see this as a bug. On the contrary, it would be more problematic if unhandled exceptions went completely untraced. Exception management should always be explicit, logged, and controlled. Falling back to a base `Exception` handler should remain the last choice.

### Possible solutions:

1. Use a pure **ASGI** middleware instead of `BaseHTTPMiddleware`.
2. Decorate your endpoints with an exception handler (valid only if just a few routes are affected).
3. Track exceptions from the stack trace and implement a proper handler (this should always be done). _Note: under high throughput, it’s recommended to write your own exception handler middleware._
4. If only a couple of routes are affected, handle them directly in the endpoint.
5. Wrap your actual middleware and on exception return 
`Response(status_code=status.HTTP_500_INTERNAL_SERVER_ERROR, content="Internal Server Error")`

An example: https://www.starlette.io/middleware/#cleanup-and-error-handling
