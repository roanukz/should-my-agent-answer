### Description

I'm trying to find a way to force FastAPI (for example when SQLAlchemy ORM detects change) to regenerate the OpenAPI schema and update `openapi.json` along with Swagger UI when something is changed in the routes. Like dynamic ENUM's or whatever.

The new schema (`app.openapi_schema`) is generated perfectly with the changes present, compared to the schema after app start. But it wont appear as a new one in the `/docs` endpoint, no matter I do. I know that the schema is cached.

I know this is asked before, but without clear resolution. I am aware that the schema generation at the app startup is the expected and normal behavior and regeneration of schema without restarting the app is quite an edge case. But I find it a necessary one.

Thank you!

## Accepted answer by luzzodev (CONTRIBUTOR)

Hello @TanelS,
there is not an official and supported way to do it.
Keeping that in mind, consider the following as a "workaround".

**General considerations:**

Far small changes that do not impact on route definition, validation. etc. you can modify directly the `app.openapi_schema` definition. For example if your want to change the title, version, some decription and so on. This operation will not require any reload.

Changes to route definitions, validation, etc., are more complex to handle because modifying the OpenAPI specs alone is not enough to affect FastAPI's request handling flow — unless you have a truly dynamic validation process in place.

**Workaround**
The app.openapi_schema is not the only thing FastAPI caches — it also caches the routes along with their dependencies. So even if you update your route information and regenerate the API schema, it will still use the 'cached' version of your routes to generate the schema.

What can you do?

    - Add the same endpoint again with its updated definition.
    - Invalidate the OpenAPI schema by setting app.openapi_schema = None.
    - Regenerate the OpenAPI schema (it will now reflect the latest routes).
    - Remove the old version of the endpoint.

Why does this work?

    - Each route is appended to the router’s internal route list.
    - For every incoming request, FastAPI iterates through this list from top to bottom and executes the first matching route.
    - OpenAPI schema generation follows the same order — but when duplicate paths exist, the last one overrides the previous definition in the schema.
    - Therefore, to fully replace a route, you must remove the earlier version (i.e. the first occurrence of that path/method combo).
      At that point, your newly added endpoint becomes both the active one for requests and the one reflected in the docs.

**Note**:

All of these changes must be made on the main FastAPI app. Any modifications applied directly to an APIRouter after it has been included in the app will have no effect.
This is an unofficial workaround, so it may break or behave differently in future FastAPI versions — don’t rely on it being officially supported.
Whenever possible, prefer using real dynamic types and properly updating the OpenAPI specs through officially supported means. Only consider hot-reloading or runtime patching when restarting the app is truly not an option.

Hope this helps.
