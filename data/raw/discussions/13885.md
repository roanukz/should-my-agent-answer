### Example Code

from typing import Union

from fastapi import FastAPI

app = FastAPI()


@app.get("/")
def read_root():
    return {"Hello": "World"}


@app.get("/items/{item_id}")
def read_item(item_id: int, q: Union[str, None] = None):
    return {"item_id": item_id, "q": q}

### Description

We deploy our apps on kubernetes. There are paths which are non-writable there, mostly root paths.

We had `fastapi[standard]==0.115.12` pinned as dependency. Now with its last release we are seeing a `fastapi-cloud-cli` being bundled, even on the earlier pinned release. I have verified the same on my local isolated virtual environment that I am now seeing a `fastapi-cloud-cli` package which was not the case two weeks back.

We invoke fastapi as : `fastapi run main.py --port xyz`

Now, with this new dependency getting injected, even on an earlier pinned version which is very surprising, caused our apps to fail deployment. The `fastapi-cloud-cli` tries to create a `/.config` file automatically on invocation of `fastapi`. Given that root path is privileged, caused our app to start failing deployments. 

I have a two fold question: 

1. Why inject this dependency on an old release? Up until last week installing `fastapi[standard]==0.115.12` DIDN'T include the `fastapi-cloud-cli`. 

2. Why break fastapi[standard]? As per the MR https://github.com/fastapi/fastapi/pull/13870 IF we DON'T want the `fastapi-cloud-cli` then we should use `fastapi[standard-no-fastapi-cloud-cli]`. But there was no such implication in the earlier releases or the docuentation. Why make it `default opt-in` for something that has been developed later? Shouldn't it be `default opt-out`? 

Debugging this proved a bit more tedious than it should have. Python doesn't seem to have a very good dependency tree visualiser. But I did find a few ways to narrow down the issue.

The interesting thing is the new `fastapi-cloud-cli` is NOT a transitive dependency(as far as the dependency tree is concerned) but somehow it is getting installed : https://pastebin.com/bEAa8rL0

> Why make it default opt-in

Agreed with @luzzodev, the idea with `standard` is to provide a set of curated default standard dependencies that would provide good defaults, the best benefits, developer experience, etc. Including the things that provide high performance, like uvloop and httptools. If there was a better tool used underneath, or a deprecated one that should be removed (e.g. as was the case with ujson and orjson), it should change there as needed. An extra is not an immutable pinned set of dependencies, for that use case, a lock would be better.

The recommended approach to handle dependencies would be to have your main package dependencies in a `pyproject.toml` or equivalent, and then an additional lock file with the exact set of packages and versions so that the installation can be replicated exactly.

You should probably use uv (https://github.com/astral-sh/uv), they have detailed instructions to use all the best practices in your Dockerfiles: https://docs.astral.sh/uv/guides/integration/docker/

An alternative would be Poetry, but I suggest uv. If you need requirements.txt then you could use pip-tools.

And as another alternative to all this, if you want to have strict pinned dependencies but still want to only use a single file with everything together, then it's probably better to not include extras for FastAPI (or any other package) and pin each dependency manually. But this would be the equivalent of doing the work of uv by hand, write the lock by hand, in a much more error prone way.

The main point is, by having a lock, you would have very direct visibility into each and all versions, and you would be able to verify in the git diff when one version of any package in all your dependencies is upgraded and if that could affect anything.
