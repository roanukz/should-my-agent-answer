### Example Code

```python
from fastapi import FastAPI

app = FastAPI(
    contact={"name": "Test", "url": "/relative-path"}  # invalid - not absolute
)

@app.get("/health")
def health():
    return {"status": "ok"}

# App starts successfully with no warning.
# GET /health works fine.
# GET /openapi.json (or /docs) throws:
#   pydantic_core._pydantic_core.ValidationError: 1 validation error for OpenAPI
#   info.contact.url
#     Input should be a valid URL, relative URL without a base [type=url_parsing, ...]
# ...5 layers deep through Starlette's exception_handler/routing internals.
```


### Description

FastAPI accepts `contact={"url": ...}` (and `license_info`) at app 
construction time without validating the URL. The value is only actually 
validated by Pydantic the first time `/openapi.json` is requested — meaning 
a mistake made when constructing `FastAPI(...)` doesn't surface until a 
completely unrelated request happens later, and then as a 500 error buried 
five layers deep in Starlette's exception handling, rather than a clear 
error pointing at the actual mistake.

### Additional Context

This surfaced in a real deployment scenario — I build contact.url dynamically based on environment (e.g. a stable production domain vs. a per-deployment execute-api URL), and one code path produced a relative string by accident. The mistake was made at FastAPI() construction time, but nothing surfaced until a completely unrelated later request to /docs — which made the actual cause much harder to trace back to its source than it should have been.

Since contact/license_info aren't validated until the first /openapi.json request, the app starts successfully and every other endpoint works fine — the failure only appears later, on a request that has nothing to do with where the actual mistake was made. The traceback also goes five layers deep through Starlette's exception-handling internals before reaching the real Pydantic error, which makes it easy to misdiagnose as a framework or Starlette bug rather than a simple app-construction typo.

## Accepted answer by sueun-dev (NONE)

The contact.url only gets validated when the OpenAPI model is built, at `OpenAPI(**output)` at the end of openapi/utils.py. FastAPI() stores it as a raw dict at construction and builds the schema lazily on the first /openapi.json or /docs hit, then caches it, so nothing else trips over it first.

Want it to fail at startup? call app.openapi() once right after you construct the app. Same ValidationError on info.contact.url, just where the typo actually is. Checked on 0.115.0, unchanged on master.
